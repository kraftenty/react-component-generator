# commit: 변경사항 분석 → 논리 단위 분류 → 한국어 커밋

변경사항을 분석해 논리적 단위로 나누고, `type: 요약` 형식의 한국어 커밋 메시지를 만들어 커밋한다.

## 실행 모드

| 모드 | 조건 | 동작 |
|------|------|------|
| 승인 모드 (기본) | 아래 자동 모드 조건이 없을 때 | 커밋 계획을 보여주고 사용자 승인 후 커밋 |
| 자동 모드 | 인자에 `--auto`가 있거나, 요청에 "바로 커밋", "승인 없이", "확인 없이", "묻지 말고" 등 승인 생략 의사가 명시됨 | 승인 단계 없이 계획을 출력만 하고 곧바로 커밋 |

- 승인 생략 의사가 **명시되지 않았으면 승인 모드**로 동작한다. 모호하면 승인 모드를 택한다.
- 자동 모드는 해당 요청 한 번에만 적용한다. 다음 `/commit` 호출에는 이어지지 않는다.
- 자동 모드에서도 Step 2의 **제외 파일 점검**과 Step 5의 안전 규칙은 그대로 적용한다.

## 워크플로우

### Step 1: 변경사항 분석

아래 명령을 병렬로 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged 변경
git diff --staged   # staged 변경
git log --oneline -10   # 기존 메시지 스타일 참고 (커밋이 없으면 생략)
```

- 변경이 전혀 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.
- untracked 파일은 `git diff`에 나타나지 않으므로 `git status`로 확인하고 필요하면 내용을 읽는다.
- diff가 매우 크면 `git diff --stat`으로 범위를 먼저 보고, 파일별로 나눠 읽는다.
- 이미 staged된 항목이 있으면 사용자가 의도적으로 고른 것일 수 있으니 임의로 unstage하지 않는다. 계획 단계에서 어떻게 다룰지 함께 보여준다.

### Step 2: 논리적 단위로 분류

변경을 **하나의 목적**을 가진 커밋 단위로 묶는다.

- 서로 다른 목적(기능 추가 / 버그 수정 / 리팩터링 / 설정 변경)은 별도 커밋으로 분리한다.
- 같은 목적을 위한 코드·테스트·문서는 한 커밋으로 묶는다.
- 한 파일에 여러 목적의 변경이 섞여 있으면 `git add -p`로 hunk 단위 분리가 가능한지 검토한다. 비대화형 환경에서는 `-p`를 쓸 수 없으므로, 분리가 어렵다면 하나로 묶고 그 사실을 사용자에게 알린다.
- 단위가 하나뿐이면 억지로 쪼개지 않는다.

**커밋하면 안 되는 파일**을 점검한다. 발견하면 제외 후보로 표시하고 사용자에게 알린다.

- 비밀 정보: `.env`, 키·토큰·인증서(`*.pem`, `credentials*` 등), diff 내 하드코딩된 시크릿
- 빌드·의존성 산출물: `node_modules/`, `dist/`, 로그 파일, `.DS_Store`
- `.gitignore`에 의도적으로 제외된 경로

### Step 3: 한국어 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

**type**

| type | 용도 |
|------|------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 빌드·설정·의존성·문서 등 기타 잡무 |

위 4가지로 분류하기 어려운 경우(테스트·문서·스타일 전용 변경 등)에도 가장 가까운 type을 고른다. 별도 type을 만들지 않는다.

**작성 규칙**

- 요약은 한국어로, 한 줄 50자 내외, 마침표 없이 쓴다. "무엇을 했는가"를 명사형 또는 `~추가`, `~수정`, `~개선` 형태로 간결하게 쓴다.
  - 좋음: `feat: 컴포넌트 생성 폼에 props 입력 필드 추가`
  - 나쁨: `feat: 여러 가지 수정함.`
- "왜"가 diff만으로 드러나지 않으면 빈 줄 뒤 본문에 한두 줄로 적는다. 자명하면 본문을 생략한다.
- diff에 실제로 있는 내용만 쓴다. 추측으로 변경 의도를 지어내지 않는다.
- `git log`에 이미 쓰는 스타일이 있으면 그것을 우선 존중한다.

### Step 4: 커밋 계획 제시 및 승인

커밋하기 **전에** 계획을 아래 형태로 보여준다. 승인 모드에서는 승인을 받고, 자동 모드에서는 계획을 출력만 하고 Step 5로 곧바로 진행한다.

```
커밋 계획 (총 N개)

1. feat: 컴포넌트 생성 폼에 props 입력 필드 추가
   - src/components/Form.tsx
   - src/types.ts
2. chore: eslint 설정 갱신
   - eslint.config.js

제외 (커밋 안 함): .env  ← 비밀 정보 포함
```

**승인 모드**
- 승인 방식은 `AskUserQuestion`으로 "이대로 커밋 / 메시지·분류 수정 / 취소" 중에서 고르게 한다.
- 수정 요청이 오면 반영해 계획을 다시 보여주고 재승인을 받는다.
- 승인 전에는 `git add`, `git commit`을 포함해 저장소 상태를 바꾸는 명령을 실행하지 않는다.

**자동 모드**
- 승인을 묻지 않는다. 계획은 사용자가 사후에 확인할 수 있도록 출력만 한다.
- 다만 아래 경우에는 자동 모드여도 **멈추고 사용자에게 확인**한다.
  - 비밀 정보로 의심되는 파일이 변경에 포함되어 있고, 제외만으로 판단하기 어려운 경우 (제외 가능한 경우는 제외하고 계속 진행)
  - 이미 staged된 항목이 논리 단위 분류와 충돌해 어떻게 처리할지 불분명한 경우

### Step 5: 커밋 실행

승인된 계획(자동 모드에서는 제시한 계획)대로 커밋 단위마다 순서대로 실행한다.

```bash
git add <해당 단위의 파일들>     # 파일명을 명시. `git add -A` / `git add .` 금지
git commit -m "$(cat <<'EOF'
<type>: <요약>

<본문 (있을 때만)>
EOF
)"
```

- 파일을 명시적으로 지정해 stage한다. 승인되지 않은 파일이 섞이지 않게 한다.
- 시스템 컨텍스트에 커밋 attribution 지침(Co-Authored-By 등)이 있으면 메시지 끝에 따른다.
- pre-commit 훅이 실패하면 원인을 보고하고 고쳐서 **새 커밋**으로 다시 시도한다. `--no-verify`로 우회하지 않고, `--amend`로 이전 커밋을 덮어쓰지 않는다.
- 커밋 하나가 끝날 때마다 `git status --short`로 다음 단위가 의도대로 남아 있는지 확인한다.

### Step 6: 결과 보고

모든 커밋이 끝나면 `git log --oneline -N`(N = 만든 커밋 수)으로 결과를 보여주고, 남은 미커밋 변경이 있으면 함께 알린다.

push는 하지 않는다. 사용자가 요청하면 그때 수행한다.

## 하지 말아야 할 것

- 승인 모드에서 사용자 승인 없이 커밋하지 않는다. 승인 생략이 명시되지 않았다면 승인 모드다.
- `git add -A`, `git add .`로 한꺼번에 stage하지 않는다.
- `--no-verify`, `--amend`, `git reset --hard`, force push 등 되돌리기 어려운 명령을 사용자 요청 없이 쓰지 않는다.
- 비밀 정보로 의심되는 파일을 커밋하지 않는다.
- 영어 메시지로 쓰지 않는다. type 접두사(`feat` 등)와 코드 식별자·고유명사만 영문을 허용한다.
